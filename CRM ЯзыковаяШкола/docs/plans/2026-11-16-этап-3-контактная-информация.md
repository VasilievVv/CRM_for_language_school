# Этап 3. Подключение Клиенты / Ученики / Сотрудники к БСП «Контактная информация»

Статус: выполнен, проверен на данных, ветка `feature/contact-info` запушена в `origin`.

## Цель

Подключить справочники `Клиенты`, `Ученики`, `Сотрудники` к подсистеме БСП 3.1.8 «Контактная информация»: табличная часть контактов, тип-владелец, виды контактной информации, формы элементов с таблицей контактов и командой добавления.

## Как БСП находит данные владельца (проверено по коду проекта)

- `УправлениеКонтактнойИнформациейСлужебныйПовтИсп.ГруппаВидаКонтактнойИнформацииПоИмениОбъекта(ПолноеИмя)` — имя группы видов = полное имя объекта без точек: `СправочникКлиенты`, `СправочникУченики`, `СправочникСотрудники`.
- Эталон реализации — `Catalog.Пользователи`: ТЧ `КонтактнаяИнформация` (13 реквизитов), `DefinedType.ВладелецКонтактнойИнформации` содержит `CatalogObject.Пользователи`, в `Catalog.ВидыКонтактнойИнформации` есть предопределённая группа `СправочникПользователи` с видами `ТелефонПользователя`, `EmailПользователя`.
- API формы: `УправлениеКонтактнойИнформацией.ПриЧтенииНаСервере(Форма, Объект, ИмяЭлементаДляРазмещения)`, `.ПередЗаписьюНаСервере(Форма, Объект, Отказ)`, `.ПослеЗаписиНаСервере(Форма, Объект)`, `.ОбработкаПроверкиЗаполненияНаСервере(Форма, Объект, Отказ)`.
- В `.mdo` владельца у БСП есть блок `<characteristics>` (связка ТЧ с `ВидыКонтактнойИнформации`, `typesFilterValue` = группа владельца). API инструмента его не создаёт — это ручной шаг.

## Блок «Характеристики» — назначение и статус

Блок `characteristics` у ТЧ объявляет её платформе таблицей значений характеристик: источник видов (`Catalog.ВидыКонтактнойИнформации`), ключ (ссылка вида), поле и значение фильтра типов (родитель = группа владельца), поля объекта, типа и значения. У `Пользователи` он заполнен как эталон.

Что проверено по коду проекта:

- Фильтрация видов по владельцу идёт **не** через этот блок: `УправлениеКонтактнойИнформацией.ВидыКонтактнойИнформацииОбъекта()` находит группу по имени объекта (`ГруппаВидаКонтактнойИнформацииПоИмениОбъекта`, `СправочникКлиенты` и т.п.) и фильтрует запросом `Где Родитель = &ГруппаВидовКИ`.
- Прямых обращений к блоку в коде подсистемы контактной информации не найдено.

Статус: **необязательный шаг**. Нужен для совместимости с эталонной разметкой БСП и для универсальных механизмов, работающих по метаданным; для базового сценария (добавить/сохранить/показать контакты, фильтрация видов) не требуется.

## Способы проверки

- Маркеры 1С: 0 ошибок по изменённым объектам.
- Ручная проверка: открыть элемент клиента → добавить телефон и e-mail → записать → переоткрыть; контакты на месте и отображаются в таблице.
- Проверка фильтрации видов: ввод контакта предлагает только виды из группы владельца. Фильтрация выполняется запросом `Где Родитель = &ГруппаВидовКИ`, группа ищется по имени объекта (`УправлениеКонтактнойИнформацией.ВидыКонтактнойИнформацииОбъекта` → `ГруппаВидаКонтактнойИнформацииПоИмениОбъекта`), то есть **не зависит** от блока `characteristics`.
- Проверить, что БСП-механизмы не падают: `УправлениеКонтактнойИнформацией.КонтактнаяИнформацияОбъекта()` возвращает данные по новым владельцам.

## Риски и ручные шаги

- Контактная информация **Клиента и Ученика независима**: у каждого свои ТЧ, своя группа видов и виды КИ; наследования/копирования от клиента к ученику нет. То же для Сотрудников.
- Всё, что не автоматизируется или рискованно (правка `.mdo` вне API, блок `<characteristics>`, права/роли), **автоматически не делаем** — оформляем отдельным разделом инструкции `docs/plans/этап-3-ручные-шаги.md`.
- Права/роли на `ВидыКонтактнойИнформации` и новые объекты — вне этапа.
